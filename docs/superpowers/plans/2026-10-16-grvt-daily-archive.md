# GRVT Daily Tick and Depth Archive Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Await user plan review and execution-method selection before implementation.

**Goal:** Collect all active GRVT perpetuals on vitalik8 and publish verified daily tick and replayable depth archives to `Ankvik-Tech-Labs/GRVT-Historical-Data`.

**Architecture:** A persistent WebSocket collector records depth with sequence validation (gap predicate derived from a captured production fixture) and UTC checkpoints. A daily job downloads bounded trade-history pages, seals each day's data into an immutable, numbered manifest revision, and publishes checksummed assets through the host's authenticated `gh` CLI. Corrections add new revisions; nothing published is ever overwritten or deleted. Persistent storage and publishing state survive collector and host restarts; local retention is immediate-cleanup-on-verified-publish rather than a fixed day count.

**Tech Stack:** Python >=3.11, requests, websockets, pyarrow, Click; pytest and Ruff; Docker Compose; cron and `flock`; GitHub CLI.

**Spec:** [Approved design](../specs/2026-10-16-grvt-daily-archive-design.md).

## Global Constraints

- All active GRVT perpetual instruments, including crypto and equities; automatically discover additions.
- Actual public executions; full aggregated L2 order book via `v1.book.d`, default 100 ms publishing interval.
- At 00:30 UTC, download the previous UTC day through all history pages.
- One release per capture date: `data-YYYY-MM-DD`, holding one or more immutable **manifest revisions** (see Task 3). No asset is ever overwritten, replaced, or deleted, for any revision, published or not; there is no mutable `manifest.json` pointer asset — the release **body** text is PATCHed, exactly once per revision and only after that revision's assets are remote-verified, to name the currently committed `manifest-rev<NN>.json`. Readers must follow that body pointer; an uploaded asset's mere presence on the release is not evidence it is part of the committed archive (resolves K1).
- Split archives below 1 GiB; GitHub releases retained indefinitely.
- **Local retention has no fixed day count.** A sealed window's staging bytes and the raw/intermediate inputs sealed into it are deleted as soon as — and only as soon as — its revision is **committed** (the body PATCH has landed) and every part hash is remote-verified. Open segments, unverified staging, and small operational state (checkpoints, discovery records, `publication.sqlite` — the durable segment/revision ledger, replacing the earlier "publication journal" — the retry queue, logs) are never pruned by this rule. See Task 3's `prune_verified` and Task 4's disk high-water behavior. GitHub then holds the only copy of pruned, committed depth windows; that is accepted, not accidental.
- **Only one unfinished (non-committed) revision per day is allowed.** `publication.sqlite` reserves segment identities and tracks each revision's `sealing → sealed → uploading → verified → committed` status in one transaction per seal; sealing revision N+1 for a day is refused while revision N for that day has not reached `committed` (resolves K3). The daily job's target-date set is `yesterday` ∪ every date with a non-committed ledger revision ∪ every date with closed depth segments not yet reserved by any revision ∪ every date still in the tick retry queue (resolves K2) — not an undefined "pending."
- Preserve numeric strings and nanosecond timestamps; expose incomplete coverage.
- Streaming container receives no GitHub credentials. Publish from the host.
- Depth sequence handling follows the gap predicate captured in `tests/fixtures/depth_protocol/` (see Task 2), not an assumed protocol. **Resync is whole-connection, not per-instrument** (resolves K5): the fixture only evidences a full reconnect, so any sequence gap closes and reopens the entire affected connection, re-subscribing every selector on it with a fresh ACK and snapshot required per instrument before its deltas are accepted again.
- The disk rollout gate (Task 5) compares the **peak co-resident footprint** — same-day raw + Parquet + tar, plus one day of accrual, plus a publish-delay reserve — against free space, not raw volume alone (resolves K7).

## Review Focus

- A market delisted before the daily download must remain in that day's collection universe; Task 1 tests the union with retained discovery records.
- Empty books and identical timestamps must remain replayable; Task 2 tests empty snapshots and orders by receipt index.
- A restart during UTC rollover must not publish an open or truncated segment; Task 2 tests recovery and Task 3 tests sealing refusal.
- A permission/rate-limit error during a later tick page must not certify a partial download as complete; Task 1 tests resumption and failure state.
- A crash after some revision-N assets are uploaded, on a release that is already public from a prior revision, must leave the release body pointing at revision N-1 until every revision-N asset is verified; Task 3 tests that the body PATCH is the only commit point and is issued exactly once, after verification (K1).
- A sequence gap on any one instrument must reconnect the whole affected connection and require a fresh ACK + snapshot per selector before deltas are accepted again, recording an outage for every instrument that was on it; Task 2 tests this against the captured fixture, not a narrower per-instrument resubscribe the fixture never evidenced (K5).
- A correction for an already-published date must never overwrite, delete, or shrink a verified asset; Task 3 tests a superset correction and a re-partitioned correction as new revisions.
- The activation day's same-day proof release and the next scheduled run's completion of that date must not collide on asset names or require reconstructing already-deleted data; Task 3 and Task 5 test the revision-1/revision-2 sequence, with `rotate_now`'s returned cutoff — never an operator-guessed instant — as the shared boundary for both datasets (K4).
- Two revisions for the same day must never be sealed concurrently, and a publish that fails on day D must be retried on every later run until it reaches `committed`, not only on D+1; Task 3 tests the one-unfinished-revision-per-day rule and the ledger-derived pending-date set (K2, K3).
- A publish retry after a crash must upload byte-identical sealed bytes, never a rebuild; Task 3 tests ledger-driven resumption.
- Disk pressure during continuous capture must trigger the documented high-water behavior, including a backoff pause rather than an immediate restart busy-loop under `unless-stopped`, never a silent drop or an unbounded fill; Task 2 and Task 4 test the thresholds, and Task 5 tests the peak-footprint gate formula (K7).

### Task 2: Continuous replayable depth capture

**Files:** Create `src/grvt_data/depth.py`, `tests/test_depth.py`, `tests/test_storage.py`; extend `storage.py` for append-only segments, crash recovery and checkpoint state.

**Interfaces:**
- `Connection(selectors: list[str])` owns one WebSocket, its `session_id` (the identity of *that connection's* subscribe ACK — one ACK, one `session_id`, for every selector on it, never per-instrument — K5), and a `DepthBook` per selector.
- `DepthBook.apply(message: dict, received_ns: int) -> list[DepthEvent]` validates continuity against the captured gap predicate (first delta's `sequence_number` must equal the owning connection's ACK's `first_sequence_number` for that selector; every later delta must equal `last_sequence + 1`; the sentinel `"0"` snapshot sequence never participates in that arithmetic) and raises `SequenceGap` when a new snapshot is required. **A `SequenceGap` on any one instrument closes and reconnects the whole `Connection`** — a new connection, a new `session_id`, every selector resubscribed with a fresh ACK and snapshot required before its deltas are accepted again, and an outage recorded for *every* instrument that was on that connection, not only the one that gapped (K5 — this capture evidences only a full connection-level reconnect; a narrower per-selector live resubscribe is not implemented because nothing demonstrates its ACK/session semantics). A delta for a selector that arrives before that selector's own post-reconnect snapshot is a protocol violation and forces another reconnect. A gap check never compares sequence numbers across a `session_id` boundary. Constructor: `DepthBook(instrument: str)`.
- `DepthBook.checkpoint(received_ns: int) -> DepthEvent` returns a full local snapshot with provenance (`session_id`, `last_sequence`).
- `SegmentWriter(data_dir: Path, dataset: str)`, `.append(row: dict) -> None`, `.close_day(day: date) -> None`, `.rotate_now() -> RotateReceipt`, `.recover() -> list[dict]` in storage. Each segment is a sequence of self-delimited frames (length-prefixed, CRC-checked); `.recover()` reads frames until the first invalid one, truncates there, and reports the discarded tail as an outage (R4) — this is what makes "truncated final raw segment records an outage" implementable for a compressed stream. `RotateReceipt` carries `cutoff_received_ns: int` (the actual instant, taken from the same apply loop that processes deltas, at which every segment closed — never a value the caller supplies) and, per instrument, the checkpoint fields (`session_id`, `last_sequence`, book state) needed so the first post-cutoff segment can continue gap-checking from exactly that state (K4).
- `async collect_depth(config: Config) -> None` performs discovery, subscriptions, capture and graceful shutdown; it owns no GitHub state. It persists the per-day discovery record Task 1's `day_universe` reads (R7), and exposes a control channel (Unix domain socket under the data root, e.g. `control.sock`) accepting a `rotate_now` command — serialized through the same apply loop as every delta, never racing it — that force-closes all open segments, writes the mid-day checkpoint, and returns the `RotateReceipt` above; this is the only sanctioned way another process (Task 5's activation-day proof release) truncates a window and learns the exact cutoff, rather than guessing one (K4, R6).

### Task 3: Verified daily archives and GitHub Releases

**Files:** Create `src/grvt_data/{archive,publish}.py`, `tests/test_archive.py`, `tests/test_publish.py`.

**Interfaces:**
- `seal_revision(config: Config, day: date, trade_report: dict, *, end_ns: int | None = None) -> Path` opens one `publication.sqlite` transaction that reserves the identities of every closed depth segment for `day` **not already reserved by a prior revision**, refuses outright if `day` already has a non-`committed` revision row (the one-unfinished-revision-per-day rule — K3), then builds the next revision's staging bundle (Parquet partitions, deterministic tar/gzip parts, per-asset SHA-256) into `staging/<day>/rev<NN>/`, writes `journal.json` before any upload is attempted, and advances the ledger row to `sealed`. Never re-slices a time window, so it never reopens or needs an already-deleted prior revision's bytes. Refuses to run against an open day. `partial_until_ns`/`manifest.json` are gone; a same-day activation run calls Task 2's `rotate_now` first, uses its returned `cutoff_received_ns` as `end_ns` for the trade download (K4), and seals only segments closed at or before that receipt.
- `publish_revision(config: Config, day: date, revision: int) -> dict` advances the ledger row through `uploading → verified → committed`. If `revision == 1` for this `data-<day>` tag: create/resume a **draft** release, upload the revision's parts and `manifest-rev01.json`, verify every remote hash (via a release-API digest if exposed, else a streaming hash of the remote copy without a second local copy — R9), set the release body to point at revision 1, then publish the draft — publishing *is* the commit point. If `revision > 1` on an already-public release: upload the revision's parts and `manifest-rev<NN>.json` as plain new, unreferenced assets (nothing points to them yet, so partial upload commits nothing); verify every remote hash; **then and only then** PATCH the release body to name this revision — that PATCH is the single visibility/commit point (K1). There is no `manifest.json` asset and no delete-then-reupload of any kind; every uploaded object is immutable from the moment it lands. A hash mismatch on an unreferenced (not-yet-pointed-to) asset deletes and re-uploads *that one asset* from the same sealed bytes (never the whole revision, never a rebuild); a mismatch discovered after the body already points at this revision is surfaced as an error, never silently corrected.
- `pending_dates(config: Config, today: date) -> set[date]` returns `{yesterday}` ∪ every date with a non-`committed` row in `publication.sqlite` ∪ every date with closed depth segments on disk not reserved by any revision ∪ every date still in the tick retry queue (K2) — this is the daily job's actual target-date set, replacing the previously undefined "pending".
- `prune_verified(config: Config, now: datetime) -> list[Path]` removes only staging/raw bytes whose containing revision has reached **`committed`** in the ledger (the body PATCH landed) and every part hash is remote-verified — no fixed day-count buffer. Open segments, any staging directory for a revision that has not reached `committed`, and small operational state (checkpoints, discovery records, `publication.sqlite` + its WAL file, the retry queue) are never touched. Also triggers automatically, ahead of the daily schedule, when Task 2's disk high-water check reports the critical threshold.
