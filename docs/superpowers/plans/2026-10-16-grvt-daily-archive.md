# GRVT Daily Tick and Depth Archive Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Await user plan review and execution-method selection before implementation.

**Goal:** Collect all active GRVT perpetuals on vitalik8 and publish verified daily tick and replayable depth archives to `Ankvik-Tech-Labs/GRVT-Historical-Data`.

**Architecture:** A persistent WebSocket collector records depth with sequence validation (gap predicate derived from a captured production fixture) and UTC checkpoints. A daily job downloads bounded trade-history pages, seals each day's data into an immutable, numbered manifest revision, and publishes checksummed assets through the host's authenticated `gh` CLI. Corrections add new revisions; nothing published is ever overwritten or deleted. Persistent storage and publishing state survive collector and host restarts; local retention is immediate-cleanup-on-verified-publish rather than a fixed day count.

**Tech Stack:** Python >=3.11, requests, websockets, pyarrow, Click; pytest and Ruff; Docker Compose; cron and `flock`; GitHub CLI.

**Spec:** [Approved design](../specs/2026-10-16-grvt-daily-archive-design.md).

## Global Constraints

- All active GRVT perpetual instruments, including crypto and equities; automatically discover additions.
- Actual public executions; full aggregated L2 order book via `v1.book.d`, default 100 ms publishing interval.
- At 00:30 UTC, download the previous UTC day through all history pages.
- One release per capture date: `data-YYYY-MM-DD`, holding one or more immutable **manifest revisions** (see Task 3). A published verified asset is never overwritten or deleted; corrections add a new revision.
- Split archives below 1 GiB; GitHub releases retained indefinitely.
- **Local retention has no fixed day count.** A sealed window's staging bytes and the raw/intermediate inputs sealed into it are deleted as soon as — and only as soon as — its revision is published (not drafted) and every part hash is remote-verified. Open segments, unverified staging, and small operational state (checkpoints, discovery records, the publication journal, the retry queue, logs) are never pruned by this rule. See Task 3's `prune_verified` and Task 4's disk high-water behavior.
- Preserve numeric strings and nanosecond timestamps; expose incomplete coverage.
- Streaming container receives no GitHub credentials. Publish from the host.
- Depth sequence handling follows the gap predicate captured in `tests/fixtures/depth_protocol/` (see Task 2), not an assumed protocol.

## Review Focus

- A market delisted before the daily download must remain in that day's collection universe; Task 1 tests the union with retained discovery records.
- Empty books and identical timestamps must remain replayable; Task 2 tests empty snapshots and orders by receipt index.
- A restart during UTC rollover must not publish an open or truncated segment; Task 2 tests recovery and Task 3 tests finalization refusal.
- A permission/rate-limit error during a later tick page must not certify a partial download as complete; Task 1 tests resumption and failure state.
- A crash after some release uploads must not expose a complete-looking archive or delete local data; Task 3 tests draft resumption and retention gating.
- A sequence gap on one instrument inside a 20-instrument connection must not invalidate the other 19 books; Task 2 tests per-instrument resync scope against the captured fixture.
- A correction for an already-published date must never overwrite, delete, or shrink a verified asset; Task 3 tests a superset correction and a re-partitioned correction as new revisions.
- The activation day's same-day proof release and the next scheduled run's completion of that date must not collide on asset names or require reconstructing already-deleted data; Task 3 and Task 5 test the revision-1/revision-2 sequence.
- A publish retry after a crash must upload byte-identical sealed bytes, never a rebuild; Task 3 tests journal-driven resumption.
- Disk pressure during continuous capture must trigger the documented high-water behavior, never a silent drop or an unbounded fill; Task 2 and Task 4 test the thresholds.

### Task 2: Continuous replayable depth capture

**Files:** Create `src/grvt_data/depth.py`, `tests/test_depth.py`, `tests/test_storage.py`; extend `storage.py` for append-only segments, crash recovery and checkpoint state.

**Interfaces:**
- `DepthBook.apply(message: dict, session_id: str, received_ns: int) -> list[DepthEvent]` validates continuity against the captured gap predicate (first delta's `sequence_number` must equal the ACK's `first_sequence_number`; every later delta must equal `last_sequence + 1`; the sentinel `"0"` snapshot sequence never participates in that arithmetic) and raises `SequenceGap` — scoped to the single affected instrument, never the whole multiplexed connection — when a new snapshot is required. A gap check never compares sequence numbers across a session boundary; a new session always resets expectations from its own ACK. Constructor: `DepthBook(instrument: str)`.
- `DepthBook.checkpoint(received_ns: int) -> DepthEvent` returns a full local snapshot with provenance.
- `SegmentWriter(data_dir: Path, dataset: str)`, `.append(row: dict) -> None`, `.close_day(day: date) -> None`, `.rotate_now() -> None`, `.recover() -> list[dict]` in storage. Each segment is a sequence of self-delimited frames (length-prefixed, CRC-checked); `.recover()` reads frames until the first invalid one, truncates there, and reports the discarded tail as an outage (R4) — this is what makes "truncated final raw segment records an outage" implementable for a compressed stream.
- `async collect_depth(config: Config) -> None` performs discovery, subscriptions, capture and graceful shutdown; it owns no GitHub state. It persists the per-day discovery record Task 1's `day_universe` reads (R7), and exposes a control channel (Unix domain socket under the data root, e.g. `control.sock`) accepting a `rotate_now` command that force-closes all open segments and writes a checkpoint — this is the only sanctioned way another process (Task 5's activation-day proof release) truncates a window; there is no ad hoc stop/restart (R6).

### Task 3: Verified daily archives and GitHub Releases

**Files:** Create `src/grvt_data/{archive,publish}.py`, `tests/test_archive.py`, `tests/test_publish.py`.

**Interfaces:**
- `seal_revision(config: Config, day: date, trade_report: dict, *, end_ns: int | None = None) -> Path` builds the next manifest revision's staging bundle (Parquet partitions, deterministic tar/gzip parts, per-asset SHA-256) into `staging/<day>/rev<NN>/`, writes `journal.json` before any upload is attempted, and returns the staging directory. It reads only closed depth segments **not already sealed into a prior revision for this day** (tracked by segment identity, never by re-slicing a time window), so it never reopens or needs already-deleted revision-N-1 bytes. Refuses to run against an open day. Replaces the old `finalize_day`; `partial_until_ns` is gone — a same-day activation run instead passes `end_ns` through to the trade download and calls Task 2's `rotate_now` control to produce a closed depth cutoff before sealing.
- `publish_revision(config: Config, day: date, revision: int) -> dict` creates/resumes a **draft** release for `data-<day>`, uploads the sealed bundle's exact journaled bytes (never rebuilding), verifies each asset's remote hash (via a release-API digest if the GitHub API exposes one; otherwise a streaming hash of the remote copy without storing a second local copy — R9), updates and re-uploads the mutable `manifest.json` pointer, then publishes. A hash mismatch on a still-draft asset deletes and re-uploads from the same sealed bytes; a mismatch discovered after publish is surfaced as an error, never silently corrected.
- `prune_verified(config: Config, now: datetime) -> list[Path]` removes only staging/raw bytes whose containing revision is **published and fully remote-verified** — no fixed day-count buffer. Open segments, any staging directory whose revision has not finished verified publish, and small operational state (checkpoints, discovery records, the publication journal, the retry queue) are never touched. Also triggers automatically, ahead of the daily schedule, when Task 2's disk high-water check reports the critical threshold.
