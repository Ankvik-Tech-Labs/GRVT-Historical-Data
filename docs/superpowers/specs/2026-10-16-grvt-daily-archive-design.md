## Selected approach

Use GRVT's historical trade API for the daily tick archive and run a continuous depth collector. GRVT documents three months of public trade retention and cursor pagination. Its depth delta feed supplies an initial full snapshot and subsequent price-level changes, with zero-size levels representing deletion. This gives daily ticks a recovery path while depth coverage starts with live capture.

| Option | Benefit | Cost / limitation |
|---|---|---|
| **Daily historical ticks + continuous depth — recommended** | Complete dated trade downloads can be retried; one persistent streaming subsystem | Ticks arrive in the archive after the daily job |
| Continuous trades and depth + historical tick reconciliation | Immediate local ticks as well as daily archives | Extra stream lifecycle and reconciliation machinery |
| Daily REST trades and sampled depth snapshots | Simplest runtime | Loses depth changes between snapshots; does not meet the proposed depth-history requirement |

Sources: [GRVT trade history](https://api-docs.grvt.io/market_data_api/#trade-history), [GRVT depth streams](https://api-docs.grvt.io/market_data_streams/#orderbook-delta).

## Collection contract

- **Universe:** all active GRVT perpetual instruments, including crypto and equities; automatically discover additions. The collector persists the per-day discovery record (instruments seen that UTC day); `day_universe` reads that record so a market delisted before the daily download still appears in that day's collection universe.
- **Ticks:** actual public executions, preserving trade ID, instrument, venue, nanosecond exchange timestamp, price, size, and taker side. At 00:30 UTC, download the previous UTC day through all history pages, bounded only by the day's own `[start_time, end_time)`; there is no dependency on when collection activated (REST trade history is retrievable for any date within GRVT's three-month window regardless of local collector uptime). `trade_history` paginates **reverse-chronologically from `end_time` toward `start_time`** using a `cursor` (confirmed from the published API reference, not assumed); `limit` defaults to 500 and has a documented max of 1000. Deduplicate by instrument/trade ID; use explicit UTC bounds and filter the output to the target day. Resume failed dates and report failures per instrument. Record per-instrument page and row counts, and confirm completion only after successful bounded cursor exhaustion (including a successful empty terminal response) and durable page finalization, with no failed or repeated cursor. Production probes confirm both API time bounds are inclusive: query inclusive bounds covering the day, then filter exactly to `[start, end)` locally. Record query bounds, observed bound semantics, pagination exhaustion and row/page counts as coverage evidence. An earliest execution hours after midnight, or an empty day, is valid; requiring an execution at the exact lower bound incorrectly rejects both (Task 1 coordinator ruling). **REST indexing lag is an explicit Task 1 exit criterion, not an assumption (round 3, N3):** Task 1 must live-probe how long after a trade executes it becomes visible through `trade_history`, and record the measured lag. A date is never sealed with an `end_time` that falls inside that measured lag window relative to the moment of the query — the 00:30 UTC job targets a day that ended 30 minutes earlier, which this probe must confirm is comfortably outside the lag, not merely assume.
- **Depth:** full aggregated L2 order book via `v1.book.d`, default 100 ms publishing interval, selectors `<instrument>@100`, subscribed production host `wss://market-data.grvt.io/ws/full`. This archives the exchange's published feed; the rate is not a promise to observe every matching-engine transition.
- **Depth sequence protocol (evidence-based, K4/K5 corrected):** captured 2026-10-16 from production (`tests/fixtures/depth_protocol/`, ~4.5 minutes across two sessions, BTC + the quiet equity AAOI, one forced reconnect; reproduced with `scripts/research/capture_depth_protocol.py` against the `websockets` package already present in an existing unrelated venv — no product dependency was installed anywhere to gather this). The full capture (not a trimmed subset) is committed, gzipped; every number below is verifiable against it. Findings, full detail in the fixture's README:
  - The subscribe ACK carries parallel `first_sequence_number`/`latest_sequence_number` arrays, one entry per selector; `first_sequence_number == latest_sequence_number + 1` for every instrument observed, within one session (never compare across sessions — see below).
  - The snapshot message's `sequence_number` is the literal sentinel string `"0"`, not a real per-update value.
  - Sequence numbers are per-instrument (per selector): two instruments multiplexed on one socket had unrelated, independently advancing ranges.
  - Within a session, sequences are strictly contiguous per instrument: across all 3030 post-snapshot deltas (2106+253 BTC, 588+83 AAOI across the two sessions), zero gaps/duplicates/reorderings occurred.
  - **What this capture does *not* evidence:** a per-instrument resubscribe on an otherwise-live multi-instrument socket. The only resync behavior actually observed is a full connection close followed by a brand-new `subscribe` naming every selector again. **Design decision (K5): resync is scoped to the whole connection, not the instrument.** On any sequence gap for any instrument on a connection, close that connection, open a new one with a new connection id, subscribe every selector again, and require a fresh ACK + fresh snapshot for each one before accepting its deltas. Record an outage for *every* instrument that was on the reconnected connection, not just the one that gapped. A delta for an instrument that arrives before that instrument's own post-reconnect snapshot is a protocol violation and forces another reconnect. This costs extra reconnects/snapshots for unaffected peer instruments on the same connection; that cost is accepted in exchange for only ever implementing evidenced behavior — a narrower per-selector live resubscribe is explicitly not implemented because nothing demonstrates its ACK/session semantics.
  - **`session_id` is client-minted, never taken from the wire (round 3, N1).** The ACK carries no session field: its JSON-RPC `id` is only the request id the client itself chose (`1` for session 1, `2` for session 2 in the capture) — reusing it as a session identity would be reading meaning into a field that has none. The client mints its own `session_id` (e.g. a UUID) at the moment it opens a connection and sends `subscribe`; that value, not anything from the server, is what `(session_id, instrument)` keys on below.
  - **Gap predicate:** track `last_sequence` per `(session_id, instrument)`; the first delta after a snapshot must equal that connection's ACK's `first_sequence_number` for the instrument; every later delta must equal `last_sequence + 1`; anything else is a gap and triggers the whole-connection reconnect above.
  - Sequence numbers are session-scoped and must never be compared across a reconnect: a forced reconnect produced a BTC `first_sequence_number` (933302) far *lower* than the prior session's last-seen value (967039) seconds earlier. Resync logic must discard the old session's counters entirely and wait for the new connection's ACK + snapshot, never diff across sessions.
  - Pre-snapshot delta ordering (buffer vs. discard) was never actually exercised — in both captured sessions the snapshot was the first message after the ACK. The protocol-violation rule above is a deliberate design choice for the unobserved case, not an empirical finding. **It needs a backoff (round 3, N1):** a venue that happened to always send a delta before its snapshot would otherwise make the client reconnect in a tight loop, each attempt immediately re-triggering the same violation. The reconnect-on-protocol-violation path uses the same backoff schedule as the disk hard-stop pause (Task 2), not an immediate retry.
  - Zero-size levels are deletions, as already assumed.
  - A quiet instrument (AAOI) went up to 4.4s between messages with no fault, confirming per-instrument silence is not a valid stall signal (see Replay, below); liveness must come from WebSocket ping/pong.
- **Replay:** save the initial snapshot, ordered deltas, connection/session identifiers, sequence/previous-sequence values, and receipt timestamps. A sequence break reconnects the whole connection and resubscribes every selector on it (see "Depth sequence protocol"); record the unavailable interval for every affected instrument. Liveness (is the socket alive) is judged by WebSocket ping/pong, never by per-instrument message silence, because quiet equities can go many seconds between book changes without any fault. **Every raw depth segment, not just the day boundary, opens with its own checkpoint as its first frame** — per-instrument `session_id`, `last_sequence`, and book state — so a segment is self-contained provenance and never depends on an external checkpoint file surviving (round 3, B2). The UTC-day-boundary checkpoint and the `rotate_now` mid-day checkpoint are both written this way, through the same book-apply loop that processes deltas (never a concurrent snapshot of in-flight state); if the collector is down at 00:00 UTC, no on-time checkpoint exists and the day's replay anchor is instead the first snapshot captured that day, with the gap recorded as an outage. **Checkpoint ownership:** a `rotate_now` checkpoint belongs to the *first segment opened after the cutoff*, not to the revision being cut off — that new segment, and the checkpoint embedded in it, belongs to whichever revision eventually seals it (round 3, B2; resolves the re-review's "which revision holds the mid-day checkpoint" question).
- **Implemented receipt/rotation provenance (Task 2 coordinator ruling):** `received_ns` is the serialized apply-loop/dequeue wall-clock sample, while raw `wire_received_ns` preserves the socket reader's sample. Depth segments and manifests declare `partition_clock: "received_ns"`. Both clocks remain true samples and may regress under clock correction. Increasing durable `receipt_index` (shared by a raw envelope and its normalized event) and exact closed segment identities define ordering/cutoff ownership, never timestamp comparisons alone. `RotateReceipt` additionally returns `cutoff_receipt_index`, `closed_segments` closed by that operation, and `partition_clock`; queued envelopes applied afterward belong to new segments despite earlier socket timestamps or a later wall-clock rollback. See [implemented storage/control contract](../../depth-capture.md).
- **First day (activation):** depth before the activation instant is permanently unavailable and labelled as such — it is never fabricated or backfilled by a later run. Ticks are not bounded by activation at all on any *later* run: the normal daily query is the same full-day `[00:00, 24:00)` UTC window used for every other day. This removes the need for any `start_ns` parameter on the trade downloader and removes the spec/plan disagreement that B1 identified: ticks are never windowed to match depth's activation cutoff.
  - **The activation-day proof release (revision 1) is the one documented exception, and its tick bound is not `end_time = now` (round 3, B4 — that phrase is wrong and is deleted).** `rotate_now`'s `cutoff_received_ns` is a **receive-clock** instant: the local wall-clock time the collector observed when it closed the depth segments. Trades are queried from GRVT by **exchange** time. Revision 1's trade download uses the numeric value of `cutoff_received_ns` as `end_time` directly — there is no separate exchange-time mapping invented for it — but the manifest records this explicitly as a receive-clock approximation of an exchange-time bound, not an exact simultaneity claim. The two clocks are not synchronized, so the boundary carries an unavoidable small overlap or gap, which is why revision 1's tick coverage for the activation day is treated as provisional, not authoritative.
  - **The next scheduled run re-downloads the *entire* activation day's ticks from `[00:00, 24:00)`, never "the rest of the day after the approximate cutoff."** Deduplicating by `(instrument, trade_id)` against revision 1's rows means this full re-download simply supersedes the provisional partial set with a complete one — there is never an attempt to stitch an exact boundary. Revision 1's tick asset is never deleted (immutability holds); the day's cumulative manifest marks it explicitly superseded by revision 2's tick asset for every instrument (see "Sealed staging..." below).
  - Older tick backfill (before the activation date) remains a separate optional operation.

### Sealed staging, manifest revisions, and corrections (resolves B1, B3, B4; corrected K1, K2, K3; round 3 fixes B1, B2, B3, B5; final gate fixes U1, U2, U3)

A capture date accumulates **manifest revisions**, numbered from 1. A revision is built once into a **sealed staging bundle**: final Parquet partitions, tar/gzip parts, and a per-asset SHA-256 computed and written to `journal.json` — a per-bundle record of exactly which sealed bytes exist and their hashes — *before* any upload begins. Builds are made deterministic so a rebuild (if ever needed before journaling) is byte-identical: tar entries sorted by path with fixed mtime/uid/gid, a fixed gzip header (`mtime=0`, empty `filename`, a fixed OS byte — not `mtime=0` alone), and pinned PyArrow writer settings (fixed compression codec, sorted row groups, pinned Arrow version). Once journaled, a part is never rebuilt — publication (including retries) only ever uploads the exact sealed bytes recorded in that bundle's journal. `journal.json` is a per-bundle artifact only; `publication.sqlite` (below) is the one durable state store across bundles and revisions (round 3, N5 — these are not two competing ledgers).

- **Each manifest is a cumulative daily index, not a per-revision delta (round 3, B2).** `manifest-rev<NN>.json` for day D lists, by name and hash, *every* asset that together makes up the day's coverage as of revision N — not only what revision N added:
  - **Depth is additive (union).** Each revision's depth segments cover a genuinely distinct, non-overlapping time window, so revision N's manifest lists revision 1 through revision N's depth parts together — the union of everything committed so far plus what N just sealed.
  - **Ticks are superseding, not additive.** Because an activation-day tick download before the day has ended is only ever provisional (see "First day (activation)"), and because a later run always re-downloads the *whole* day rather than a remaining slice, a later revision's tick asset for an instrument **supersedes** an earlier revision's tick asset for that same instrument — the manifest marks the earlier one `superseded_by: <rev>` rather than listing both as current. The earlier tick asset is never deleted (immutability still holds); it is simply no longer part of current coverage.
  - **The cumulative index itself is persisted durably in `publication.sqlite`, not reconstructed from local files.** Building revision N+1's manifest reads the ledger's own stored index for revisions 1..N and adds what N+1 just sealed — it never needs to re-open or re-derive from local raw/Parquet bytes that may already have been pruned after an earlier revision's verified commit. This is what makes "pruned bytes never needed again" actually true, not just asserted.
- **No mutable pointer asset (K1), with one narrow, bounded exception for self-correction (round 3, B1).** There is no `manifest.json` asset of any kind, and no asset ever referenced by **any public release's body** — currently or at any point in the past; a draft's body does not count, matching U3's state-based reading — is ever overwritten or deleted. The one allowed deletion: an **uncommitted** revision's own freshly-uploaded asset that has **never been referenced by any public release's body** may be deleted and re-uploaded to fix a corrupt upload or a hash mismatch, strictly while that revision has not yet reached `committed`. Once a revision is committed, none of its assets — nor any earlier revision's — can ever be deleted again. (A prior draft of this spec called every asset immutable "published or not," which GitHub's lack of in-place asset replacement made impossible to honor for a mismatch fix; this is the corrected, narrower rule.)
- **One state-based definition of "committed" (final gate, U3 — this single sentence replaces the two earlier, contradictory commit-point claims, "the body PATCH is the commit point" and "publishing is the commit point"):** a revision N is **committed if and only if the remote release is public and its body points to revision N's cumulative manifest — `manifest-rev<NN>.json`, named by revision and SHA-256 — whose referenced assets were remote-verified** before that body content was put in place. "Committed" is a predicate on observable remote state, never the name of one particular API call. The two flows *reach* that state through different final transitions: a release that starts absent has its draft fully prepared first (assets uploaded and remote-verified, the desired body text already set on the draft), and the **publish transition** is what first makes the predicate true; an already-public release has this revision's assets uploaded and remote-verified first, and the **body PATCH** is what makes the predicate true. Neither transition is itself the definition. GitHub release metadata (the release's own description/body text) can be edited in place without touching any asset. That body text is the single source of truth for "which revision is canonical": `Active revision: <N>, manifest-rev<N>.json, sha256 <hash>`, plus a short human-readable coverage summary. Readers of a release must read the **public** release's body to find the committed manifest; a draft is never committed, whatever its body already says, and the presence of an asset on the release is not, by itself, evidence that it is part of the committed archive. Re-issuing the same body content is always safe and idempotent (round 3, N6) — it is not a one-shot action that must never repeat, only one that must never *advance past* what verification actually confirmed.
  - **Routing is by the release's observed remote state — absent, draft, or public — never by the local revision number (round 3, B5).** A prior draft of this plan branched on `revision == 1` to decide "create a draft" vs. "upload to an existing public release," which breaks the moment a crash leaves revision 1's draft published but the local ledger not yet marked `committed`: a retry would wrongly re-enter the "create a draft" branch against an already-public tag. The corrected flow queries GitHub for `data-<date>`'s actual state before acting:
    - **Absent:** create a draft, upload this revision's parts and `manifest-rev<NN>.json`, verify every hash remotely, set the draft's body to the desired committed content, then publish the draft — the publish transition is what first makes the committed predicate true (the release becomes public with a verified body pointer); the draft, even with its body set, is not committed (U3).
    - **Draft (exists, not yet published):** resume uploads into that same draft — do not create a second one — verify, set the body, publish.
    - **Public:** upload this revision's parts and `manifest-rev<NN>.json` as new, unreferenced assets; verify every hash; then PATCH the body — on an already-public release, the body PATCH is the transition that makes the committed predicate true for this revision (U3).
  - **Crash reconciliation always treats the remote as ground truth, synced into the local ledger — never the reverse.** Before taking any action, a retry reads the release's actual remote state *and* its current body-pointer content directly from GitHub. If the remote already satisfies the committed predicate for this revision — the release is public and its body names this revision's manifest and hash (U3; reconciliation tests the actual remote state, never "which call succeeded last") — but the local `publication.sqlite` row never advanced to `committed` because the process crashed between the remote call succeeding and the local write, the retry recognizes this from the remote read, advances the local row to `committed` to match, and does **not** attempt to create a second draft or re-issue a redundant PATCH as if nothing had happened. A hash mismatch on an asset never referenced by ANY public release body re-uploads *that one asset* from the same sealed bytes, never a rebuild and never the whole revision; a mismatch discovered after the revision is committed (the public release's body already points at it) is never silently corrected — surfaced as an error requiring the next revision.
- **Durable segment ledger and one-unfinished-revision-per-day (K2, K3).** A small SQLite database, `publication.sqlite`, under the data root is the durable ledger — counted as small operational state, never touched by cleanup (see "Retention and disk budget"). Sealing a revision is one SQLite transaction that: reserves the identities of every closed depth segment it is about to seal (so a later seal can never claim the same segment twice, and a seal never needs to re-slice a time window or touch an already-sealed-and-deleted segment), writes/advances that revision's row through `sealing → sealed → uploading → verified → committed`, and records that revision's contribution to the day's cumulative index (above). **Only one unfinished (non-`committed`) revision is allowed per day.** Sealing revision N+1 for a day is refused while revision N for that day is not yet `committed`; the daily job must finish N (resume uploads, verify, and complete the committing transition — publish the prepared draft, or PATCH the public release's body, as the observed remote state requires) before a new revision can be sealed for that day.
- **The daily job's target-date set excludes the current UTC day; membership follows unfinished work (round 3, B3; final gate U2).** For a past date, unfinished work means a non-`committed` revision; unreserved closed depth segments; an incomplete full-day tick download in the retry queue (including a committed activation revision's provisional ticks); or an unresolved failed/deadline-exceeded/interrupted attempt on a nonterminal date, even when the parent crashed before worker spawn and no checkpoint exists. Such dates remain pending across UTC rollover. `pending_dates()` contains every past date with unfinished work, plus **yesterday only if never collected/attempted** (no revision row and no `per_date_runs` row). This first-ever selection starts each fresh yesterday even when no depth was captured. Other dates enter only for unfinished work. A date is **terminal** once its latest revision is committed under the remote U3 predicate, its full-day ticks are complete, and no non-committed revision, unreserved closed segment, or retry entry remains. Reconcile a stale attempt against those facts; an old failure status alone cannot make a terminal date pending. **Terminal yesterday drops out: repeated `daily` runs create no revision, seal, tick download, asset upload, or release write for any terminal date.** The set can therefore be empty after backlog drains. Newly closed unreserved segments or a new retry requirement make a previously terminal date pending again. **"Open" means exactly `date >= today_utc`.** Such a day is refused by `seal_revision`'s normal path. This differs from a segment's open/closed state: a `.open` segment is still being written and becomes closed on rotation regardless of calendar day; today's closed segments wait until tomorrow unless processed by the explicit activation exception below.
- **Activation-day completion is that one documented exception, not a generally-available bypass (final gate, U2 — one flag, one numeric format, a defined target set):** revision 1 for the activation date requires an operator to have called `rotate-now` and obtained a `RotateReceipt` first — `rotate-now` prints the receipt's actual `cutoff_received_ns` as a plain numeric nanosecond integer, and that printed value is passed back verbatim. The operator then invokes `daily --allow-today --end-time-ns <cutoff_received_ns>`. `--end-time-ns` takes the int64 nanosecond value exactly as printed — there is no ISO-8601 form of this option anywhere; an earlier draft's `--end-time <UTC-ISO8601>` is deleted as unrunnable against a nanosecond receipt. `--allow-today` makes the run's target-date set **exactly `{today_utc}`** — it never augments the normal set: if `pending_dates()` is non-empty, the flagged run refuses to start, and the operator must first drain the pending set with an ordinary `daily` run — a drain that actually terminates, because under the work-based membership rule above a committed, fully-drained yesterday is terminal and drops out of the set rather than re-entering it every night (U2: the refusal is a satisfiable precondition, not a permanent block). `--end-time-ns` is valid only together with `--allow-today`, applies only to that single today date (the normal daily run is unchanged — it takes no end bound, excludes the current day, and seals every other date on its own full `[00:00, 24:00)` window), and a value outside today's UTC window is rejected. This is the only path that is allowed to seal and publish a same-day, still-open date. Depth covers activation up to the receipt's cutoff; ticks use the receipt's `cutoff_received_ns` as a receive-clock approximation of `end_time` (see "First day (activation)" above), explicitly provisional. The activation run durably queues its provisional ticks for a full-day download; the next scheduled run finds the activation date through that unfinished-work marker once it is no longer today, re-downloads the full day's ticks (superseding revision 1's partial set per the cumulative-manifest rule above), and seals revision 2 from segments reserved after revision 1's cutoff — never reopening or needing revision-1 data that has already been deleted post-verification.
- One release per **capture date**, e.g. `data-2026-10-16`, holding one or more revisions as described above. Split archives below 1 GiB. GitHub's per-release asset count limit (believed ~1000, not yet verified — round 3, N7) is a hard cap that grows monotonically as immutable revisions and split parts accumulate; `status` reports the current asset count, and a day that would exceed the limit **fails outright rather than pruning anything** to make room — pruning an asset to stay under the cap would violate immutability, so running out of headroom is a configuration/scope problem to fix (fewer parts, larger split threshold, or similar), not something the pipeline resolves by deleting data.
- Each revision's manifest (`manifest-rev<NN>.json`) records instrument universe, requested and observed intervals, row counts, depth rate, outages, successful/failed tick downloads, hashes, schema version, and per-instrument coverage start/end, per the cumulative-index rule above. A missing instrument or stream cannot be silently called complete.
- **Locking (round 3, B6, B8):** every publication-mutating public CLI entry — `daily`, `publish`, and any exposed `seal`-equivalent — acquires `state/run-daily.lock` itself, once, at its own top level, before calling any archive/publish function; archive/publish functions and the internal per-date worker entry never acquire it themselves, so there is no nested acquisition. `rotate-now` takes no publication lock — it only talks to the collector's control socket. See "Deployment paths and schedule" for exactly where this lock is taken and how a timeout is logged. Verify remote asset content hashes using a release-API digest if one is exposed; otherwise stream-hash the remote copy without storing a second local copy. Retries resume from the ledger and reuse the same sealed bytes; interrupted uploads remain recoverable.
- **Per-date isolation (round 3, B9; strengthened for slow and hung dates, final gate U1):** the daily job processes **yesterday first when pending**, then the remaining pending dates oldest-first — a backlog can never push yesterday to the end of the run. One date's failure never blocks another's, and the hard per-date deadline is enforced at a **process boundary, never by request timeouts alone**:
  - **Parent/worker structure.** The parent `daily` CLI acquires the global `state/run-daily.lock` once at its own top level (the B6/B8 lock discipline is unchanged), then for each target date spawns an **isolated per-date worker process in its own process group**, invoking an internal, *unlocked* entry point — the worker never acquires the lock again. It and any mutating descendants retain the inherited lock descriptor for their lifetimes, so even a parent crash cannot permit a new writer while an old worker remains alive. The parent watches a monotonic wall-clock deadline per date (**default 60 minutes, configurable**); when it expires, the parent **terminates the entire worker process group** (SIGTERM, then SIGKILL after a bounded 5-second grace, waiting for the worker and its descendants to exit before advancing), so a CPU-bound in-process sealing step (Parquet normalization, tar/gzip, hashing), a trickling HTTP response that keeps every socket read under its own timeout, or a hung `gh` subprocess is stopped by the deadline plus that bounded termination grace. The parent then durably records `deadline_exceeded` for that attempt and continues with the next date.
  - **Call bounds are defense in depth, not the mechanism.** Inside the worker, every external call (HTTP request, subprocess) is additionally bounded by the remaining deadline; workers also check the monotonic deadline between pages, segments, parts, and streamed response chunks — each timeout shrinks as the budget drains — so most overruns fail promptly and cleanly; but these timeouts are an optimization for clean failure, and the process-group kill is the enforcement. A `requests` timeout is per-socket-operation, not total-duration, which is exactly why the kill boundary exists.
  - **Progress is resumable, never lost to the kill.** Tick pages (Task 1's durable page writes, including cursor and deduplication state), closed/reserved segments, sealed journal entries, and uploaded parts are all checkpointed atomically. A retry reuses each verified page/part and resumes from the last durable boundary, rather than starting the date's tick download at page 1 or rebuilding a sealed part. A date that ends `deadline_exceeded` or `interrupted` therefore remains pending and can complete across attempts even when one attempt exceeds the budget.
  - **Durable per-date attempt ledger, `per_date_runs`, in `publication.sqlite`** (minimal schema, distinct from the revision-status enum `sealing → … → committed`, which tracks a revision's publication rather than an attempt): `day` (UTC date), `attempt_id` (monotonic per day), `status` ∈ {`running`, `completed`, `failed`, `deadline_exceeded`, `interrupted`}, `started_at_ns` (integer), `ended_at_ns` (integer, nullable), `error` (text, nullable); primary key `(day, attempt_id)`. The parent commits `running` before spawning the worker and the terminal status when the worker ends, always before the next date starts.
  - **Stale `running` recovery:** on the next successful acquisition of the global lock, before deriving `pending_dates()`, any prior `running` rows are flipped to `interrupted` with an end timestamp and recovery reason — the exclusive lock proves no active writer can coexist. Derive recovery candidates from attempted nonterminal dates, including attempts with no local checkpoint (crash before worker spawn), across UTC rollover. Any required remote reconciliation runs inside the supervised worker deadline before sealing/downloading: unfinished work resumes, while a remote commit completed just before the crash is synced locally and returns without creating another revision. A date already known fully committed and complete is terminal despite the stale attempt status. Attempt status is a recovery hint, not a reason to create another revision after all work is done.

The process exits non-zero if any date failed or exceeded its deadline, but only after every target date got its own attempt unless the outer safety bound ends the run — a permanently stuck, hung, or merely slow old date can never prevent yesterday's run from completing, because yesterday runs first and every date's worker is killable. The wrapper's `timeout --kill-after=30s 6h` (below) is a final safety net only, never the isolation mechanism. The 60-minute default is explicitly provisional until measured: Task 5's rollout gate times an actual full per-date cycle — download, seal, upload — and records whether a real day completes inside the default or resumes across attempts, and the configured default is set from that measurement.

### Retention and disk budget (resolves B5; supersedes the earlier seven-day rule; corrected K7)

- **Local retention:** no fixed day-count buffer. A sealed window's staging bytes and the raw/intermediate inputs sealed into it are deleted as soon as — and only as soon as — its containing revision is **committed** (the U3 predicate holds: the remote release is public with its body pointing at this revision's verified manifest — not merely "uploaded") *and* every one of its part hashes has been remote-verified. Currently open (`.open`) segments, any staging directory for a revision that has not reached `committed`, and small operational state (checkpoints, the per-day discovery/universe record, `publication.sqlite` and its WAL file, the incomplete-tick retry queue, logs) are never pruned by this rule regardless of age. **Accepted consequence:** once a revision is committed and locally pruned, GitHub holds the only copy of that window's live-captured depth — there is no second local copy by design, because immediate pruning was explicitly authorized. The restore path for a later re-partitioned correction to an already-pruned window is downloading that window's committed parts back from the release, never re-deriving from local raw (which no longer exists). Hash verification happens once, at commit time; there is no later re-check of already-committed remote bytes.
- **Maximum tolerated publish outage is explicit, not implied (round 3, N2):** because uncommitted bytes are never pruned, a stuck publish (GitHub down, auth broken, network partition) only ever grows local disk — it frees nothing. At the measured capture rate, that growth consumes the `publish_delay_reserve_days` allowance from the Task 5 rollout gate (default one day) and then starts eating the gate's safety margin; left stuck roughly one more day beyond that, the 2 GiB hard stop is reached and the collector itself pauses, with the gap recorded as an outage. "Never silently drops data" holds throughout, but the bound on how long publishing can stay broken before the collector itself stops is exactly `publish_delay_reserve_days` plus whatever margin the gate measurement left — not indefinite.
- **High-water behavior, fractions of total filesystem capacity (not current free space):** the collector/CLI watch the data root filesystem's **total capacity** and current free bytes. Below 20% free-of-total, `status` and logs report a degraded warning. Below 10% free-of-total (or 10 GiB, whichever is larger), the daily job immediately runs verified cleanup ahead of schedule and the collector stops growing the subscribed universe (it keeps capturing already-subscribed instruments) until free space recovers above the warning line. Below 2 GiB free, the collector flushes and cleanly closes its current open segments and exits non-zero rather than risk a corrupt partial write; it never silently drops data to keep running. **The container does not simply restart into the same full-disk condition:** on a hard-stop exit, the collector writes a pause marker with a backoff schedule; on the next start (whether from `unless-stopped` or manual), it checks free space and the marker first — if still below the hard-stop line, it waits out the backoff and re-checks rather than immediately subscribing and exiting again in a restart busy-loop.
- **Measured rollout gate, peak co-resident footprint, before the daily cron block is installed (Task 5):** run the collector against the full discovered universe for a measured 1–2 hour window and record observed raw bytes/sec, projected bytes/day, per-instrument rate outliers, and the compression ratio from one sealed build (Parquet + tar vs. raw). Also time an actual date's download, sealing, verification/upload, and total wall time, recording per-attempt timing and whether the day completes under the provisional configurable 60-minute default or resumes across attempts. Record the observed coverage and set the configured budget from the measurement with stated margin; an estimate at 2 req/s alone is not runtime evidence. The gate compares **peak co-resident usage**, not raw volume alone, against free space: at 00:30 UTC on day D+1, before day D's revision is committed, disk holds day D's raw segments, D's normalized Parquet, and D's tar parts *simultaneously*, while day D+1's raw is already accruing from 00:00. Gate formula: `day_D_raw + day_D_parquet_and_tar (raw × measured compression ratio) + one_day_raw_accrual (D+1) + publish_delay_reserve`, where `publish_delay_reserve` is a fixed allowance (configurable, default one additional day of raw) for the time a revision can sit uploaded-but-not-yet-committed. Only install the cron block if that peak stays under 50% of the data root filesystem's free space at measurement time; otherwise reduce scope or add storage first. This replaces both "measure after deployment" and the earlier raw-only formula with a go/no-go check before continuous rollout is relied upon.
- Keep GitHub releases indefinitely — remote retention is unchanged and remains indefinite.
- Use host GitHub authentication for publication; keep credentials outside Git and outside the streaming collector's environment.
